# 02 — pe: Bir Dosyayı Çözmek

`winspect pe <path>` bir `.exe` ya da `.dll` dosyasını **çalıştırmadan**, sadece
baytlarını okuyarak çözer. Hiçbir process yok, sadece diskteki dosya. Bu yüzden
ilk seferde doğru çalışması en kolay komut ve en iyi öğretici: çıktını PE-bear
gibi bir araçla yan yana koyup doğrulayabilirsin. Dosya: `src/pe.c`.

İşlediğimiz sıra:
```
DOS header → e_lfanew → PE signature → File Header → Optional Header
   → Section tablosu → Imports (IAT) → Exports (EAT)
```

---

## 1. Önce güvenlik: dosya düşmandır

Bir PE dosyası **güvenilmez girdidir**. Bozuk ya da elle hazırlanmış bir dosya,
herhangi bir alana saçma bir sayı koyabilir. O sayıya körü körüne uyarsak
tamponun (buffer) dışını okuruz — çöker ya da güvenlik açığı doğar.

Bu yüzden `pe.c`'de dosyaya dokunmanın **tek yolu** şu fonksiyondur:

```c
static int read_at(const struct pe_file *f, size_t off, void *dst, size_t len)
{
    if (off > f->size || len > f->size - off) {
        return 0;   // [off, off+len) aralığı dosyanın tamamen içinde değil
    }
    memcpy(dst, f->data + off, len);
    return 1;
}
```

İki ince nokta:

- Kontrol neden `len > size - off` şeklinde, `off + len > size` değil? Çünkü
  `off + len` **taşabilir** (overflow): iki büyük sayı toplanınca küçük, "geçerli"
  görünen bir sayıya dönebilir. Önce `off > size` kontrol edilir ki `size - off`
  asla negatife düşmesin (alt taşma olmasın).
- Neden `memcpy` ile yerel bir yapıya kopyalıyoruz, pointer'ı doğrudan buffer'a
  cast etmiyoruz? Çünkü `e_lfanew` herhangi bir değer olabilir — hatta **tek
  sayı**. Hizalanmamış (misaligned) bir struct pointer'ını dereference etmek
  C'de **tanımsız davranıştır**. x64 donanımı buna göz yumsa da derleyicinin
  optimizasyonu "bu asla olmaz" varsayabilir. `memcpy` bu tuzaktan kaçınır.

Aynı mantıkla string okumak için `read_cstr` var: dosya sınırını aşmadan,
NUL'a kadar okur ve her zaman sonuna NUL koyar.

---

## 2. DOS header: MS-DOS'tan kalma 64 bayt

Dosyanın ilk 64 baytı MS-DOS uyumluluğundan kalmadır. Bugün sadece iki alan
önemli:

- **`e_magic`**: İlk iki bayt diskte `4D 5A` = `'M' 'Z'`. x86 **little-endian**
  olduğu için düşük adresli bayt WORD'ün düşük baytıdır, yani bir WORD olarak
  okuyunca `0x5A4D` çıkar. Bu `IMAGE_DOS_SIGNATURE`. Bu imza yoksa dosya PE değil.
- **`e_lfanew`**: "Asıl NT header'lar şu offsette" diyen pusula. Bir sonraki
  adıma buradan atlıyoruz.

```c
if (dos.e_magic != IMAGE_DOS_SIGNATURE) { /* PE değil, reddet */ }
if (dos.e_lfanew <= 0) { /* negatifse dosyanın başından önceyi gösterir, reddet */ }
```

`e_lfanew` işaretli (signed) bir `LONG`. Negatif bir değer dosyanın başından
öncesini gösterir; unsigned offset'e çevirmeden önce bunu reddediyoruz.

---

## 3. PE signature ve File Header

`e_lfanew`'in gösterdiği yerde 4 baytlık imza var: `50 45 00 00` =
`'P' 'E' '\0' '\0'` → little-endian `0x00004550` = `IMAGE_NT_SIGNATURE`.

Hemen ardından **File Header** gelir: dosyanın kaba kimliği.

- **Machine**: Hangi CPU için derlenmiş (AMD64 mı, I386 mı, ARM64 mı).
- **NumberOfSections**: Kaç bölme var.
- **TimeDateStamp**: Eskiden derleme zamanıydı. Modern Microsoft build'leri
  "tekrarlanabilir" (reproducible) olduğundan buraya gerçek zaman yerine bir hash
  koyar — bu yüzden çözünce çoğu zaman saçma bir tarih çıkar.
- **Characteristics**: Bayraklar (çalıştırılabilir mi, DLL mi, vb).

Bayrakları basmak için veri tablosu deseni (bak: [01-mimari](01-mimari.md)):

```c
static const struct flag_name file_flags[] = {
    { IMAGE_FILE_EXECUTABLE_IMAGE, "EXECUTABLE_IMAGE" },
    { IMAGE_FILE_DLL,              "DLL"              },
    ...
};
```

`print_flags` bu tabloyu gezer, set olan her biti ismiyle basar. Tabloda olmayan
ama set olan bitleri de hex olarak gösterir — hiçbir şey saklanmaz.

---

## 4. Optional Header: adı yanıltıcı, zorunlu

"Optional" aslında yanlış isim: her `.exe`/`.dll` imajının bir Optional Header'ı
vardır. Bu, yükleyicinin (loader) dosyayı RAM'de çalışan bir imaja çevirmesi için
**yol haritasıdır**.

İki farklı düzeni var, başındaki **Magic** WORD'ü ile ayırt edilir:
- `0x10B` = **PE32** (32-bit), `ImageBase` 32-bit bir alan.
- `0x20B` = **PE32+** (64-bit), `ImageBase` 64-bit bir alan.

Bu yüzden önce sadece Magic'i okuyup hangi struct'ı kullanacağımıza karar
veriyoruz:

```c
WORD magic;
read_at(&f, opt_off, &magic, sizeof magic);
if (magic == IMAGE_NT_OPTIONAL_HDR32_MAGIC) { /* IMAGE_OPTIONAL_HEADER32 oku */ }
else if (magic == IMAGE_NT_OPTIONAL_HDR64_MAGIC) { /* IMAGE_OPTIONAL_HEADER64 oku */ }
```

Bastığımız önemli alanlar:

- **AddressOfEntryPoint**: Programın ilk çalışacak komutunun RVA'sı. Gerçek
  adres = `ImageBase + bu RVA`.
- **ImageBase**: Yüklenmek istediği "rüya" adres (ASLR bunu kaydırabilir).
- **SectionAlignment / FileAlignment**: Bellekte (genelde 4 KB sayfa) ve diskte
  (genelde 512 B sektör) hizalama. İkisinin farklı olması, Raw ≠ Virtual
  ayrımının sebebidir.
- **Subsystem**: GUI mi (pencere açar) yoksa konsol mu (CUI).
- **DllCharacteristics**: Modern güvenlik anahtarları — ASLR (`DYNAMIC_BASE`),
  DEP (`NX_COMPAT`), Control Flow Guard (`GUARD_CF`). Bu bitlerin **eksik** olması
  gerçek bir güvenlik sinyalidir, o yüzden hepsini açıkça basıyoruz.

---

## 5. Section tablosu: kargo etiketleri

Her bölme (section) için bir `IMAGE_SECTION_HEADER` vardır. Tablonun başladığı
yer çok kritik:

```c
size_t sec_off = opt_off + fh.SizeOfOptionalHeader;
```

Dikkat: `sizeof(IMAGE_OPTIONAL_HEADER64)` **değil**, dosyanın kendi beyan ettiği
`fh.SizeOfOptionalHeader`. Bu, PE parse etmede **en sık yapılan hatadır**: struct
boyutuna güvenirsen section tablosunu yanlış offsetten okursun.

Her section'ın gösterdiğimiz alanları:

- **Name**: 8 ham bayt, 8 karakterse **NUL ile bitmeyebilir**. Bu yüzden
  `%-8.8s` kullanıyoruz: en fazla 8 bayt okur, alanın dışına taşmaz.
- **VirtualAddress / VirtualSize**: RAM'deki yeri ve boyutu.
- **PointerToRawData / SizeOfRawData**: Diskteki yeri ve boyutu.
- **Characteristics → R/W/X**: İzinler. Bu üçlü, DEP/NX garantisinin
  dosya-seviyesindeki kaynağıdır: `.text` `r-x` (kod okunur+çalışır ama yazılamaz,
  kod kendini değiştiremesin), `.data` `rw-` (veri okunur+yazılır ama çalışmaz,
  veri kod sanılıp çalıştırılamasın).

`.bss`'in diskte boyutu 0'dır (raw 0), çünkü sadece sıfırlardan oluşur; RAM'de
yer kaplar ama diskte baytı yoktur. Bu, Raw ≠ Virtual farkının en net örneği.

---

## 6. RVA → dosya offset çevrimi

Burası Faz 3'ün kalbi. Import ve export tablolarının içindeki her pointer bir
RVA'dır (bellekteki yer), ama diskte veri başka yerdedir. Çeviri section
tablosuyla yapılır:

```c
static int rva_to_off(const IMAGE_SECTION_HEADER *sections, unsigned n,
                      DWORD rva, size_t *out)
{
    for (unsigned i = 0; i < n; i++) {
        DWORD va  = sections[i].VirtualAddress;
        DWORD raw = sections[i].SizeOfRawData;
        if (rva >= va && rva < va + raw) {      // bu section rva'yı kapsıyor
            *out = sections[i].PointerToRawData + (rva - va);
            return 1;
        }
    }
    return 0;
}
```

Mantık: "rva hangi section'ın sanal aralığına düşüyor? Düştüğü section'da, sanal
başlangıçtan ne kadar ileriyse, diskteki başlangıçtan da o kadar ileridedir."
Sadece **raw** (diskte gerçekten var olan) aralığı eşliyoruz; `.bss` gibi diskte
olmayan adresleri reddediyoruz.

Bu yüzden section tablosunu bir **diziye** sakladık (tek seferde basıp geçmedik):
import/export çözerken sürekli bu diziye başvuruyoruz.

---

## 7. Imports (IAT): bu dosya neyi ödünç alıyor

Import tablosu `IMAGE_IMPORT_DESCRIPTOR` dizisidir, her DLL için bir kayıt, sonda
sıfırlanmış bir kayıtla biter. Her kayıt iki paralel diziye işaret eder:

- **OriginalFirstThunk (INT)**: İstenen fonksiyon isimleri/ordinalleri (diskte
  sabit kalır).
- **FirstThunk (IAT)**: Çalışma anında yükleyicinin gerçek adreslerle doldurduğu
  kutular.

Diskte dosyayı okuduğumuz için **OriginalFirstThunk**'ı geziyoruz (isimler orada
duruyor; IAT ancak canlı process'te anlamlı). Her thunk ya bir isme işaret eder
(`IMAGE_IMPORT_BY_NAME` = Hint + isim) ya da ordinal numarasıyla import eder
(en yüksek bit set ise). 32/64-bit thunk boyutu ve ordinal biti farklı olduğundan
koda `is64` parametresi veriyoruz.

Güvenlik bağı: **IAT hooking**. Bir antivirüs ya da zararlı, IAT'deki bir kutuyu
değiştirip çağrıyı kendi üstünden geçirebilir. Program fonksiyonu çağırırken
ezbere adrese gitmez, IAT'deki kutuya bakar — o kutu değiştirilmişse çağrı
kaçırılmış olur.

---

## 8. Exports (EAT): bu DLL neyi sunuyor

Export tablosu bir `IMAGE_EXPORT_DIRECTORY` ve üç paralel dizidir:

- **AddressOfNames**: İsimlerin RVA'ları (sıralı, ikili arama için).
- **AddressOfNameOrdinals**: Her isim için `AddressOfFunctions`'a indeks.
- **AddressOfFunctions**: Her ordinal için kod RVA'sı (ya da forwarder string).

`GetProcAddress` tam olarak bu üçlüyü gezer: ismi bul → ordinal'i oku → adresi
döndür. Biz de aynısını yapıyoruz.

**Forwarded export**: Bazı fonksiyonlar bu DLL'de kod değildir; başka bir DLL'e
yönlendirilir. Örneğin `kernel32.dll`'deki birçok fonksiyon aslında
`ntdll.dll`'e forward edilir (`"NTDLL.RtlAllocateHeap"` gibi bir string). Bunu,
fonksiyonun RVA'sı export dizininin **kendi aralığına** düşüyorsa anlarız; o zaman
bir kod adresi değil, bir yönlendirme stringi okuruz.

`.exe`'ler genelde export etmez (`Exports (none)` normaldir), DLL'ler eder.

---

## 9. Çıktıyı doğrulamak

`pe`'nin güzelliği: çıktını bağımsız bir araçla karşılaştırabilirsin.

- **PE-bear** ya da **CFF Explorer**: görsel, yan yana koy.
- **WinDbg**: `!dh <modül>` komutu header'ları döker.
- **objdump** (MinGW ile gelir): `objdump -x dosya.exe` — section'lar, imports,
  entry point hepsi.

Entry point, ImageBase, section RVA/raw değerleri bu araçlarla **birebir** tutmalı.
Tutuyorsa parser'ın doğru demektir.

Sıradaki: [03 — inspect](03-inspect.md), statik dosyadan canlı process'e geçiş.
